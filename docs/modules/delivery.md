# Website Delivery, Checklists (SOPs) and Timelines

> Runs a client project from kickoff to handover. Three per-project tabs on the project screen share this area: **Delivery** (the whole run as a rail of stages read off the project's own SOP checklist, with the page-by-page build grid, a generated Google Sheet tracker, per-page QC and a derived launch-readiness verdict), **Checklist** (the flat, editable view of the same SOP checklist) and **Timeline** (a Gantt/list of phases and milestones). SOP templates are authored in the **Checklist Creator** (`/modules/checklist-creator`, optionally generated by Gemini). A daily cron emails each team member their dated, assigned, unfinished delivery steps and tasks. Users are the internal `@activeset.co` team; clients see only projections of this data through the client portal and a read-only public share view.

## Key flows

1. **Checklist creation (the arc's source).** Checklist tab → pick 1+ templates → `ChecklistOverview` calls `checklistService.createChecklist(projectId, ids)` ([ChecklistService.ts](../../src/services/ChecklistService.ts)). Each id resolves built-in first (`getTemplateById`), else `sop_templates/{id}`; none found → default `webflow_migration_v1`. `instantiateTemplate` spreads every section/item and assigns fresh `sec_`/`item_` ids; sections are concatenated; `agencyBasicsFor` (line ~149) prepends "Start: client setup" and appends "Close: handover & sign-off", skipping any step whose normalized title already exists; `templateIds` records every source. Written with `addDoc` to `project_checklists`.
2. **Rendering the Delivery tab.** `DeliveryTab` subscribes to pages (`deliveryRepository.subscribeToPages`) and checklists (`subscribeToProjectChecklists`); `deliveryArc(checklists)` makes one `SectionStage` per section (sorted by `order`, key `${checklistId}:${sectionId}`) and, if no section has role `pages`, splices a `pages` entry after the last `kickoff` stage (else at index 1). `currentStageKey` picks the earliest unfinished section once. `StageScreen` renders `StageChecklist` and the role extras; `gateFor` lists blocking items in earlier stages but nothing is disabled. Ticking calls `checklistService.updateItemStatus` — same item the Checklist tab edits.
3. **Page tracker and sheet.** "Import from sitemap" (`ImportPagesDialog` → `importFromLinks`) adds `project.links` whose normalized path is not already tracked, in batches of 400; "Add a page" (`addPage`) rejects duplicate paths. Status cells call `setPageWork` (dotted `work.<id>` path). "Generate/update sheet" → `syncSheet` → POST sheet route `{action:'sync'}` → `syncTrackerSheet`: loads project + pages (admin), `buildTrackerRows`, creates the spreadsheet on first run (title `<client> – <name> · Website Project Tracker`) or clears and rewrites the `Project Tracker` tab, then merges `delivery.trackerSheetId/Url/SyncedAt`. Share → Drive reader permission with `sendNotificationEmail=false`. Import → `previewSheetImport` (picks a tab matching `tracker|pages|project`, parses by header text) then `applySheetImport` (match existing pages by lowercased title, fill only blank fields, overwrite `work.*` statuses present in the sheet; new rows get a slug path).
4. **Launch readiness.** At the `launch` stage `LaunchExtras` computes `pageChecksFor(stack, project.delivery)` (saved list, else stack defaults), `itemsWithRole(checklists,'launch')`, and `buildAuditsByPageId` (page path ↔ `project.links[].auditResult`). `buildLaunchReadiness` → ready only if pages exist, every page's applicable disciplines are settled, no page blocked, no launch item pending, and every per-page check passes (`resolveCheck`: person answer, else scan verdict, else pending). QC clicks call `setPageCheck` (dotted `qc.<id>`), with a toast when the answer disagrees with the scan.
5. **Agency basics backfill and template feedback.** `AddAgencyBasics` runs `basicsGap` per checklist in the browser, then `judgeBasicsGap` → `/api/delivery/basics-gap` (Jev re-judges resemblances when configured) and replaces the answer if `judged`. Saving calls `checklistService.addAgencyBasics` → `sectionsWithBasics` (joins an existing section of the same title, else adds a new start/close section) → `updateSections`. `TemplateImprovements` loads each source template (`getSOPTemplate`), runs `improvementsFor`, and saves chosen items via `saveTemplateImprovements` → `applyImprovements` → `updateSOPTemplate`; built-ins throw a "duplicate it first" `DatabaseError`.
6. **Daily nudge.** Vercel cron → `/api/cron/delivery-nudge` → `gatherDeliveryNudges` ([delivery-nudge.ts](../../src/lib/delivery-nudge.ts)) → `buildDigest` ([delivery.nudge.ts](../../src/modules/delivery/domain/delivery.nudge.ts)) → for each person `sendDeliveryNudgeEmail`, then `sendDeliveryDigestEmail` to `NOTIFY_EMAIL`. Use `?dryRun=1` with the cron secret to preview.

## Gotchas and invariants

- **A project checklist is a deep copy taken at creation.** Changing templates or `AGENCY_START`/`AGENCY_CLOSE` never reaches existing projects; they need "Add the standard steps" (`delivery.basics.ts`). Whenever something must be true of every project, check both custom templates and already-running projects (memory: delivery-arc-design).
- **Do not hardcode per-project step lists.** Kickoff/launch/site-wide lists are checklist sections tagged with a role; the only list kept in code is per-page QC (`defaultPageChecks`), because a checklist has no page axis — and even that is stored per project once edited (`delivery.pageChecks`). Rehan rejected TypeScript-constant step lists on 2026-09-19 (memory: no-hardcoded-per-project-lists).
- **Roles are the only hardcoded stage concept**: `kickoff`, `pages`, `client_review`, `launch` (`StageRole` in [types/index.ts](../../src/types/index.ts)). Legacy `section.stage` is still read by `roleOf` ([delivery.arc.ts:74](../../src/modules/delivery/domain/delivery.arc.ts)); `applyImprovements` clears `stage` whenever it writes a role, or the old tag would win.
- **Built-in SOP templates (`webflow_migration_v1`, `branding_v1`) are code and cannot be written.** `saveTemplateImprovements` refuses them ([ChecklistService.ts](../../src/services/ChecklistService.ts), `if (template.isBuiltIn)`); the Creator only offers "Duplicate & Edit". Most real projects run from custom templates in `sop_templates`.
- **Template improvements match by title**, because instantiation drops any link to the source item. Renaming an item on a project makes it read as "added"; sections missing from the template are skipped entirely ([delivery.feedback.ts](../../src/modules/delivery/domain/delivery.feedback.ts) `byTitle`).
- **Every checklist item edit rewrites the whole `sections` array** after a non-transactional read (`updateItemStatus` etc., [ChecklistService.ts:223](../../src/services/ChecklistService.ts)). Two people ticking different items at the same moment can lose one write. `updateChecklistItemValues` merges the value map but still rewrites the array. Pages, by contrast, use dotted field paths ([delivery.repository.ts:269](../../src/modules/delivery/infrastructure/delivery.repository.ts), `:286`) so two people editing two columns of one row do not collide.
- **`movePage` is not really transactional**: it calls `getDocs` (not `tx.get`) inside `runTransaction` ([delivery.repository.ts:496-497](../../src/modules/delivery/infrastructure/delivery.repository.ts)), so the read is not part of the transaction.
- **Page identity is the normalized path** (`normalizePagePath`: pathname only, leading slash, no trailing slash). The audit join in `buildAuditsByPageId` is by path string; `sourceLinkId` is written but never read.
- **Sheet import does not normalize paths.** `parseTrackerRows` sets `path` to the full staging URL when it is one, and `applySheetImport` stores it verbatim ([delivery-sheet-sync.ts:222](../../src/lib/delivery-sheet-sync.ts)); import also matches existing pages by title, not path.
- **The generated sheet is a view.** Every sync clears `A1:ZZ10000` of the `Project Tracker` tab and rewrites it; edits in the sheet are lost. If that tab is renamed/deleted, sync returns 409 rather than creating a new spreadsheet ([delivery-sheet-sync.ts:98](../../src/lib/delivery-sheet-sync.ts)), so the client's link is never orphaned.
- **`drive.file` scope**: the service account can only see files it created or that were explicitly shared with its email. Importing a team member's existing sheet returns "could not be found, or this app has no access" (404) unless that sheet is shared with the service account.
- **Unknown is not fail.** `resolveAutoCheck` returns `unknown` for unscanned pages and for Jev probabilities between `0.35` and `0.75` ([delivery.progress.ts:97](../../src/modules/delivery/domain/delivery.progress.ts)); those thresholds mirror `JEV_THRESHOLDS` in `src/lib/jev-qa.ts` and must be changed together. A person's non-pending answer always wins (`resolveCheck`, line ~203). Saved `pageChecks` with an unrecognized `auto` have the signal dropped (`pageChecksFor`).
- **Stack page checks are not copied onto the project on first Launch visit** (despite the `StackDefinition` doc comment): `pageChecksFor` falls back to stack defaults until someone saves via "Edit checks" ([delivery.progress.ts:329](../../src/modules/delivery/domain/delivery.progress.ts)).
- **Gates never lock.** `gateFor` only reports; `StageScreen` shows a warning and keeps everything editable. `blocking` is opt-in per item.
- **`includePages` is never passed as `false` outside tests**, so brand projects (`branding_v1`) still get a "Pages" stage spliced in.
- **Client approvals are append-only and tick nothing internal.** Only the portal route writes `delivery.approvals` (merge, first timestamp kept) — see [client-portal.md](client-portal.md).
- **Nudges only chase dated, assigned, team-member steps**, and stop when a project is `closed`/`paid`/`paused`, when every item is completed/skipped, or when nothing is outstanding ([delivery-nudge.ts:53-54](../../src/lib/delivery-nudge.ts), [delivery.nudge.ts](../../src/modules/delivery/domain/delivery.nudge.ts) `skipReasonFor`). Reads are capped at 400 projects and 800 checklists with no ordering, so beyond that some are silently skipped. Emails are sent sequentially on purpose (Gmail throttling).
- **Crons must build links from `NEXT_PUBLIC_BASE_URL`** (via `getBaseUrl`), not the request host (memory: cron-internal-urls).
- **The kickoff email is never sent by the app** — copy only. `KickoffExtras` does not pass `portalUrl`, so the portal link line never appears in the draft.
- **Timeline Markdown replace is destructive and lossy**: `handleReplaceFromMarkdown` calls `clearTimeline` then `importParsed` ([ProjectTimelineOverview.tsx:287](../../src/modules/timeline/ui/screens/ProjectTimelineOverview.tsx)); a failure in between leaves the project with no timeline, and the Markdown format carries no `clientVisible`, `assignee` or `notes`, so a round trip hides every milestone from the client portal.
- **Timeline edits rewrite the arrays** (`_writeTimeline`). The timeline is the team's own schedule: what the client sees is the client plan (`projects/{id}.clientPlan`), whose stages follow this module's checklist sections (see [client-portal.md](client-portal.md) → the plan). The old per-milestone "Visible to client" switch is gone; the flag is still read, only to keep a pre-plan portal showing what it showed.
- **Checklist section titles now also shape the client's tracker.** The client plan classifies each section into a stage kind by its title (then its role), so renaming "Step 7: QA" to something without a review word can move its steps to a different client stage. Keep review/QA, launch and handover wording recognisable in SOPs.
- **The Markdown template format is load-bearing.** The Creator round-trips the whole template through `templateToMarkdown`/`parseMarkdownToTemplate` on every tab switch; a field the format drops is deleted on save. `values` is intentionally never written ([template-export.ts](../../src/lib/template-export.ts) header; asserted in its test).
- **No local Firebase credentials on Rehan's Mac**: delivery screens were verified with fixture data, typecheck, lint, tests and build only (memory: delivery-arc-design). For local rendering see memory local-preview-setup.
